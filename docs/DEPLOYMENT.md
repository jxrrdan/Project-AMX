# Deploying AMX to production (AWS)

This is the end-to-end runbook. Everything below is wired in code: the CDK stacks in `infra/cdk`, the images in `apps/*/Dockerfile`, and the pipelines in `.github/workflows`. What the repository cannot do for you is create the AWS account, own the domain, or obtain third-party credentials. Those are the **one-off steps** in section 1.

## What runs where

| Concern | Production |
|---|---|
| SPA | S3 + CloudFront (security headers, HSTS, CSP, SPA routing via a viewer-request function) |
| API | ECS Fargate, 2 to 6 tasks (CPU autoscaling), behind an ALB with AWS WAF |
| Database | Aurora PostgreSQL Serverless v2, credentials in Secrets Manager |
| Live workshop board | Socket.IO over WebSocket at `/api/socket.io`, fanned out across tasks through ElastiCache Redis |
| Files | Private S3 bucket, read through its own CloudFront distribution (origin access control) |
| Email / AI / PDF | SES / Bedrock / headless Chromium in the API image |
| CAPTCHA | Cloudflare Turnstile |
| Secrets | Generated by Secrets Manager (JWT, CAPTCHA, VHC link, webhook); third-party keys pasted in once |

The API validates its own configuration at boot (`apps/api/src/common/config/production-config.ts`). In production it **refuses to start** on dev default secrets, short secrets, wildcard or localhost CORS, or any mock driver. A misconfigured deploy fails the health check and rolls back rather than serving traffic insecurely.

## 1. One-off setup

1. **AWS account and region.** `eu-west-2` (London) is the default. Run `cdk bootstrap` once.
2. **GitHub OIDC role.** Create an IAM role GitHub Actions can assume, and save its ARN as the secret `AWS_DEPLOY_ROLE_ARN`.
3. **Domain.** Request an ACM certificate in **us-east-1** for your hostname (validate it with a DNS record in Cloudflare). Save `DOMAIN_NAME` and `CERTIFICATE_ARN` as repository variables. After the first deploy, add a Cloudflare CNAME from the hostname to the `DistributionDomainName` output of `Ams-Edge`.
4. **SES.** Verify the sending domain (DKIM, SPF, DMARC) and request production access to leave the sandbox. Save `EMAIL_FROM`.
5. **Bedrock.** In the Bedrock console, enable access to the Claude models you want, then save the inference-profile IDs as `BEDROCK_REASONING_MODEL` (analysis, assistant) and `BEDROCK_LIGHTWEIGHT_MODEL` (chatbot, short drafts).
6. **Repository variables:** `AWS_REGION`, `DOMAIN_NAME`, `CERTIFICATE_ARN`, `EMAIL_FROM`, `BEDROCK_REASONING_MODEL`, `BEDROCK_LIGHTWEIGHT_MODEL`, and after the first deploy `WEB_BUCKET_NAME`, `CLOUDFRONT_DISTRIBUTION_ID` (stack outputs of `Ams-Edge`).
7. **Third-party credentials**, pasted into Secrets Manager after the first deploy (the secrets exist but hold placeholders): `TurnstileSecret`, `TurnstileSiteKey` (Cloudflare dashboard), `DvlaApiKey` (DVLA developer portal). Then force a new API deployment.

## 2. Deploy

Merge to `main`. `.github/workflows/deploy.yml`:

1. Verifies lint, tests and build.
2. Creates the `ams-api` ECR repository if needed and pushes the API and migration images.
3. Deploys the data tier (network, Aurora, Redis, storage, queues, auth).
4. Runs `prisma migrate deploy` as a one-off ECS task. Migrations run **before** new code rolls out, so write them backward compatible (add columns before using them; remove them a release later).
5. Deploys compute, edge and observability. ECS rolls tasks with a circuit breaker that rolls back automatically on failed health checks.
6. Runs the migration task again (no-op normally, but this is the first real migration on a brand-new environment).
7. Publishes the SPA to S3 and invalidates CloudFront.

`.github/workflows/ci.yml` runs on every pull request: lint, unit tests, builds, `npm audit` (fails on critical), CDK synth and Docker builds of all three images.

## 3. First production data

Do not run the seed script in production: it creates a demo agent with a well-known password. Instead create the first agent and its principal user with the bootstrap script, as a one-off ECS task using the `migrate` image (it has the tooling and the same DB environment):

```bash
aws ecs run-task --cluster <ClusterName> --launch-type FARGATE --task-definition ams-migrate \
  --network-configuration "awsvpcConfiguration={subnets=[<PrivateSubnetIds>],securityGroups=[<MigrateSecurityGroupId>],assignPublicIp=DISABLED}" \
  --overrides '{"containerOverrides":[{"name":"MigrateContainer","command":["npm","run","bootstrap:dealer"],"environment":[
    {"name":"BOOTSTRAP_DEALER_NAME","value":"BMW Northampton"},
    {"name":"BOOTSTRAP_SUBDOMAIN","value":"bmwnorthampton"},
    {"name":"BOOTSTRAP_ADMIN_EMAIL","value":"principal@example.co.uk"},
    {"name":"BOOTSTRAP_ADMIN_FIRST_NAME","value":"Alex"},
    {"name":"BOOTSTRAP_ADMIN_LAST_NAME","value":"Whitfield"}]}]}'
```

The generated one-time password is printed once in the `/ams/migrate` log group; the principal must change it at first sign-in. The script refuses to touch an agent that already exists, validates its inputs, and enforces a 12-character minimum if you supply your own password. Everyone else is invited from the app.

## 4. Operating it

- **Health:** `GET /api/health` (liveness) and `GET /api/health/ready` (database). The ALB uses `/ready`.
- **Logs:** CloudWatch `/ams/api`, `/ams/migrate`. Alarms and the `ams-operations` dashboard are in `Ams-Observability`.
- **Locked-out user:** an admin calls `POST /users/:id/unlock`. See also `docs/runbooks/`.
- **Rotating a secret:** update it in Secrets Manager and force a new deployment. Rotating the JWT secrets signs everyone out; rotating `VHC_LINK_SECRET` invalidates emailed health-check links.
- **Rollback:** redeploy the previous image tag (`ams-api:<git sha>`). If a migration was involved, ship a forward fix; do not hand-edit the schema.
- **Backups:** Aurora keeps 7 days of continuous backup plus a final snapshot on stack removal. Test a point-in-time restore before go-live and record the result in `docs/runbooks/aurora-failover.md`.

## 5. Still your decision or dependent on third parties

These cannot be completed from the repository and are the honest remaining items before real customers:

- **Third-party integrations that need contracts and credentials:** BMW RIS MQTT feed (`-c enableMqttSubscriber=true` once the subscriber image and credentials exist), AutoTrader / Motors.co.uk, Xero / Sage / QuickBooks, Stripe billing. These are modelled in the schema but mocked.
- **SMS:** the Twilio driver is implemented; set `SMS_DRIVER=twilio` and its three variables in the task definition once you have an account.
- **Penetration test and Mantis scan** (see `docs/SECURITY.md`), a data-protection impact assessment and ICO registration (UK GDPR), and a privacy notice and cookie text for the public forms.
- **Load test** against a staging copy: the autoscaling thresholds and Aurora capacity range are sensible starting points, not measured ones.
- **Staging environment:** deploy the same stacks to a second account or region with a different `domainName` before production.
